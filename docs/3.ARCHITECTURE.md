# Shadow Heist — Architecture

## 1. System overview

Shadow Heist is a Vite + React frontend with a Solidity/FHEVM contract layer. The project deliberately separates the polished local demo from the live chain adapters so the experience can be explored without a wallet while the privacy path remains inspectable and testable.

```text
React UI
  ├─ App state machine
  ├─ Demo game rules
  ├─ Wallet chooser
  │    ├─ Injected EIP-1193 provider
  │    └─ WalletConnect Ethereum provider
  └─ Live adapter boundary
       ├─ ethers contract calls
       ├─ Zama SDK encrypted inputs
       └─ Zama SDK public decryption

Sepolia / local Hardhat
  └─ ShadowHeist.sol
       ├─ create / join match
       ├─ import encrypted euint8 actions
       ├─ homomorphic rule evaluation
       ├─ encrypted random event
       └─ public result handles after resolution
```

## 3. Frontend state machine

`App.tsx` owns the current demo state:

- `view`: `lobby`, `waiting`, or `game`.
- `wallet`: current connected wallet session or `null`.
- `walletModalOpen`: whether the wallet chooser is visible.
- `joinCode` and `matchCode`: local match identity in demo mode.
- `opponentJoined`: waiting room seat state.
- `selectedAction`: current local action.
- `processing`: simulated encryption and resolution stages.
- `result`: revealed local result.
- `timers`: cancelable demo timers.

The next live slice should add `liveMatchId`, `liveMode`, transaction hashes, and chain-derived state without replacing the demo branch.

## 4. Wallet architecture

`src/chain.ts` provides one normalized `WalletSession` shape for two providers:

- `injected`: browser wallet exposed through `window.ethereum`.
- `walletconnect`: lazily imported `@walletconnect/ethereum-provider` with QR modal.

Both paths create an ethers `BrowserProvider`, validate chain ID `11155111`, obtain a signer, and return the normalized address. The injected path does not attempt to programmatically disconnect; clearing local state is the correct browser-wallet behavior. WalletConnect sessions call the provider disconnect method.

## 5. FHEVM architecture

`src/fhevm.ts` uses the current `@zama-fhe/sdk`:

1. Configure the browser provider for Sepolia.
2. Call `sdk.encrypt` with a typed `euint8` action.
3. Pass `encryptedValues[0]` and `inputProof` into the contract.
4. Read result handles after `resolveRound`.
5. Call `sdk.decryption.decryptPublicValues` for publicly decryptable handles.

The contract imports `FHE`, `euint8`, `externalEuint8`, and `ZamaEthereumConfig` from `@fhevm/solidity`.

## 6. Contract lifecycle

1. `createMatch` creates player one and assigns round 1.
2. `joinMatch` assigns player two.
3. Each player calls `submitAction` with an encrypted action and proof.
4. `resolveRound` computes encrypted comparisons and points.
5. The contract marks action and result handles publicly decryptable.
6. The client reads handles and requests public decryption.

## 7. Current boundary and next slice

The visible UI is still demo-driven. `src/liveGame.ts` already contains live functions:

- `createLiveMatch`
- `joinLiveMatch`
- `submitLiveAction`
- `resolveLiveRound`
- `readLiveMatch`
- `decryptLiveRound`

The next implementation should connect those functions to the React state machine and introduce a stable match ID/share-link format.
