# Shadow Heist — Database and Persistence

## 1. Current decision

The MVP does not use an application database. This is intentional: the game is designed as a small protocol demo, and the core match state belongs on the FHEVM contract rather than in a centralized application database.

## 2. Where data lives today

### Browser memory
The React app stores demo state in component state:

- current view
- match code
- opponent status
- selected action
- simulated processing state
- local scoreboard
- revealed result
- wallet session

Reloading the page clears this data.

### Smart contract
`ShadowHeist.sol` stores:

- match ID counter
- player one and player two addresses
- round number
- plaintext score fields reserved for future verified score aggregation
- submission flags
- resolution flag
- encrypted player actions
- encrypted outcome
- encrypted player points
- encrypted random event code

### Wallet provider
The wallet provider owns the account/session state. The app stores only the normalized session needed for the current browser session.

## 3. Contract data model

```text
Match
  playerOne: address
  playerTwo: address
  round: uint8
  scoreOne: uint8
  scoreTwo: uint8
  playerOneSubmitted: bool
  playerTwoSubmitted: bool
  roundResolved: bool
  actionOne: euint8
  actionTwo: euint8
  outcome: euint8
  pointsOne: euint8
  pointsTwo: euint8
  eventCode: euint8
```

## 4. No database needed for the demo

Do not add a database just to store UI state. It would introduce ownership, synchronization, privacy, and deployment complexity without improving the core demonstration. A public match can be reconstructed from contract events and reads.

## 5. Future indexing option

If the game grows into a public multiplayer product, add an indexer or read model rather than putting sensitive actions in a traditional database. A future read model could store:

- match ID
- player addresses
- creation and join timestamps
- current lifecycle status
- transaction hashes
- chain ID
- public result status

It must never store plaintext player actions before the contract permits reveal.

## 6. Privacy requirements

- Never persist a plaintext action before resolution.
- Do not log encrypted input proofs or wallet signatures unnecessarily.
- Treat public result handles as decryptable after resolution.
- Do not put private keys, WalletConnect secrets, or signing material in a database.
- If analytics are added, collect aggregate events such as `lobby_viewed` or `match_started`, not player strategy.

## 7. Migration trigger

Introduce persistence only when at least one of these becomes real:

- durable share links that must work after reload
- matchmaking across many concurrent players
- match history
- leaderboards
- moderation or abuse reporting
- analytics requiring cross-session attribution
