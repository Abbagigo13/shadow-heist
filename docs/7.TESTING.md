# Shadow Heist — Testing

## 1. Testing goals

Testing should prove three things:

1. The demo remains explorable and visually coherent.
2. The contract enforces player and round invariants.
3. The live adapters pass correctly typed encrypted inputs and read/decrypt outputs through the intended interfaces.

## 2. Current commands

```bash
pnpm build
pnpm contracts:compile
pnpm contracts:test
```

The frontend build runs TypeScript checking and Vite production compilation. The contract test runs through Hardhat.

## 3. Current automated coverage

`test/ShadowHeist.cjs` verifies:

- a match can be deployed;
- player one can create a match;
- player two can join;
- emitted lifecycle events contain the expected addresses;
- initial round state is correct;
- an unresolved match is not falsely marked resolved.

## 4. Contract test matrix to add

### Access control

- non-player cannot submit an action;
- player one cannot join their own match;
- a third address cannot join a full match;
- duplicate action submission reverts;
- resolve before both actions reverts;
- resolve twice reverts.

### Game rules

Test all action pairs:

- Steal beats Scout.
- Guard beats Steal.
- Scout beats Guard.
- Equal actions draw.
- Player two’s mirrored wins produce the correct outcome.
- Random event stays within the expected bound.

### Privacy lifecycle

- external encrypted input is accepted with a valid proof;
- the action is stored as an encrypted handle;
- the result handles are created only after resolution;
- result handles are marked publicly decryptable after resolution.

## 5. Frontend manual checks

Use the Preview app and verify:

- lobby loads without a wallet;
- create flow reaches waiting room;
- simulate rival unlocks the game;
- each action can be selected and deselected;
- submit progresses through all processing labels;
- result card reveals both actions and points;
- next round and rematch reset the correct state;
- toast dismiss works;
- wallet modal opens and closes;
- browser-wallet path reports missing wallet clearly;
- WalletConnect path reports missing project ID clearly when not configured;
- layout works at desktop and mobile widths;
- keyboard focus is visible.

## 6. Wallet integration checks

With a browser wallet:

1. Use Sepolia.
2. Connect from the wallet chooser.
3. Confirm the shortened address appears.
4. Disconnect and confirm the UI returns to the disconnected state.
5. Test a wrong network and verify the actionable message.

With WalletConnect:

1. Set `VITE_WALLETCONNECT_PROJECT_ID`.
2. Open the WalletConnect option.
3. Scan the QR code from a mobile wallet.
4. Approve on the mobile wallet.
5. Confirm the session address and Sepolia chain.
6. Disconnect and reconnect.

## 7. Live Sepolia acceptance test

After the live UI is wired:

1. Deploy the contract to Sepolia.
2. Connect wallet A and create a match.
3. Share the match ID/link with wallet B.
4. Connect wallet B and join.
5. Submit different actions from both wallets.
6. Confirm no plaintext action is shown before resolution.
7. Resolve the round.
8. Publicly decrypt the result handles.
9. Confirm the revealed actions and outcome match the encrypted computation.
10. Confirm transaction links and errors are understandable.

## 8. Regression discipline

Run `pnpm build` after frontend changes. Run `pnpm contracts:compile` and `pnpm contracts:test` after Solidity, Hardhat, or dependency changes. Do not rely on a green demo simulation as proof that the live contract path works.
