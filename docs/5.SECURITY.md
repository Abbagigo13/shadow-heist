# Shadow Heist — Security

## 1. Threat model

Shadow Heist protects the secrecy of player choices until a round is resolved. It does not currently promise anonymity, private wallet balances, resistance to every front-running strategy, or production-grade economic security.

Relevant actors:

- A curious observer reading the chain.
- A malicious player attempting to submit twice or submit for another player.
- A compromised browser or wallet.
- A malicious or misconfigured frontend.
- A future relayer or indexing service.

## 2. On-chain controls

The contract currently enforces:

- only the match creator can be player one;
- a second player cannot be the same address as player one;
- only the two assigned players may submit actions;
- each player can submit only once per round;
- actions require an FHEVM external input proof;
- a round cannot resolve before both players submit;
- a resolved round cannot resolve again;
- result handles are made publicly decryptable only after resolution.

## 3. FHE privacy boundary

Player actions are imported as encrypted `euint8` values using `FHE.fromExternal`. The contract compares and selects encrypted values, so the contract does not branch on plaintext actions.

After `resolveRound`, the action handles and result handles are marked with `FHE.makePubliclyDecryptable`. This is the intended reveal boundary. The client then uses the Zama SDK to request public decryption.

Public decryption means the result is intentionally public after the reveal. It is not a mechanism for keeping final results private forever.

## 4. Wallet security

- The app never requests or handles a private key.
- WalletConnect uses a public project ID, not a signing secret.
- The browser wallet remains the authority for signatures and transactions.
- The app rejects chains other than Sepolia.
- The app displays a clear error when the WalletConnect project ID is absent.
- Injected wallets cannot be forcibly disconnected by a website; local session clearing is used instead.

## 5. Secrets and configuration

Safe browser configuration:

- `VITE_WALLETCONNECT_PROJECT_ID`
- `VITE_SHADOW_HEIST_ADDRESS`

Never place these in the frontend:

- wallet private keys
- seed phrases
- Hardhat deployer mnemonics
- WalletConnect secret keys
- Zama mainnet API secrets
- Infura private server credentials

Hardhat variables are configured through `pnpm hardhat vars set` and must not be committed.

## 6. Contract risks still requiring review

- `scoreOne` and `scoreTwo` are currently stored but not updated by verified public decryption.
- The contract does not yet encode a timeout or forfeiture path for a player who never submits.
- The public decryption proof is not submitted back to the contract for score settlement.
- Random event semantics should be reviewed for fairness and boundedness.
- There is no replay or match expiry policy.
- Production deployment requires an independent smart contract review.

## 7. Frontend risks

- Demo mode intentionally simulates the rival and result locally.
- A UI label must never be treated as proof that a transaction was mined.
- Live mode must derive status from receipts and contract reads.
- The frontend should not trust a URL match ID without validating chain state.
- User-facing error messages should avoid exposing raw provider internals.

## 8. Security checklist before mainnet

- Add encrypted-input integration tests.
- Add negative tests for unauthorized players and duplicate submissions.
- Add tests for all nine action combinations.
- Implement verified score settlement using the Zama decryption proof path.
- Add match expiry and griefing controls.
- Run static analysis and a professional review.
- Use a dedicated mainnet Zama API configuration, never a testnet assumption.
